Run Cortex as a systemd user service

Cortex runs in the foreground with cortex or cortex serve. To keep it running without a terminal, install a per-OS-user systemd unit with cortex service.

Commands

cortex service install            # --listen, --root, --data, --public-origin, --trust-proxy accepted
cortex service start
cortex service stop
cortex service restart
cortex service status
cortex service logs
cortex service logs --follow
cortex service uninstall

The user unit is written to ~/.config/systemd/user/cortex.service and managed with systemctl --user and journalctl --user-unit cortex.service.

Install behavior

service install resolves the executable to a stable absolute path, refuses empty, relative or transient paths, writes the unit atomically with a versioned integrity header, reloads systemd, and enables and starts the service. An existing unit that is not managed by Cortex is never overwritten or removed silently, and lifecycle commands refuse to operate on a foreign or hand-modified unit. status reports enabled/running state, PID, version, listen address and a live health check of the public GET /api/health endpoint (a minimal {"ok":true} JSON response; the richer /api/status endpoint stays behind browser authentication), and exits nonzero when the service is failed or missing. uninstall preserves all Cortex configuration, conversations and data.

GitHub CLI authentication

Running cortex from your login shell inherits your session environment, so gh auth status and other CLI tools work exactly as in your shell, including the GitHub token in your login keyring. A systemd user unit starts with a minimal environment, so the unit records HOME and, when ~/.config/gh/hosts.yml exists, GH_CONFIG_DIR — Cortex and its agent subprocesses then keep using your GitHub CLI authentication without copying any file or token. Because a user service runs inside your user session it can still reach your login keyring; if that keyring is locked, run gh auth login once in the session first. A future system-wide service would run under a dedicated account with no login keyring and would need gh auth login for that account or an explicit token in its environment.

User-service limitation

cortex service manages a per-OS-user systemd service. System-wide mode (cortex service install --system) is a documented follow-up and is not yet supported. OpenCode's own configuration and session data remain isolated in per-run temporary directories.
